# DECISIONS.md — decisions made while implementing TASK_PLAN.md

Per `TASK_PLAN.md` §0.1 rules 2 and 10, unrelated defects and ambiguous choices
are recorded here instead of being silently changed or blocking work.

## M0-01 — Scaffolding, settings, logging

- **Legacy admin commands moved, not refactored.** `main.py` had to become a
  thin entrypoint, so the four legacy command handlers (`/maintenance`, `/list`,
  `/profile_of_user`, `/ban`, `/unban`, `/banned_list`) were lifted verbatim out
  of `main.py` into `handlers/legacy_commands.py` and registered through
  `register_all_handlers`. This is a **path-only** change: behavior (including
  bug **B1**, the ineffective `/maintenance` toggle) is intentionally preserved
  and will be fixed in M0-05 when the handlers are ported onto `app.services`.
- **`app.settings` field names are snake_case.** pydantic-settings maps env vars
  case-insensitively, so `BOT_TOKEN`, `VPN_TOKEN`, `OWNER_IDS`, `DATABASE_URL`,
  etc. all resolve to their lowercase attributes. This matches the accessor
  names used elsewhere in the plan (`settings.timezone`, `settings.database_url`).
- **Secret masking threshold.** `SecretMaskingFilter` only masks secrets of at
  least 8 characters, to avoid replacing ordinary short strings with `***`.
  Real Telegram/panel tokens are always far longer, so this does not weaken the
  guarantee.
- **Legacy top-level modules are excluded from the gate for now.** `config.py`,
  `loads.py`, `middlewares.py`, `utils.py`, and the top-level `handlers/`
  package still carry many pre-existing defects; they are ported and deleted in
  later M0 tasks. To keep M0-01's gate meaningful, `pyproject.toml` marks them
  `ignore_errors` for mypy. They are intentionally left type-unclean until the
  tasks that own them port the code.
- **`mypy` stays installable via `py3xui`.** `py3xui` declares `mypy` as a
  runtime dependency, so moving `mypy` to `requirements-dev.txt` still works —
  it arrives transitively at runtime. The explicit pin only guarantees the dev
  version.

## M0-02 — Database layer

- **Naive UTC everywhere (`base.utcnow()`).** SQLite has no native timezone-aware
  timestamp type and drops `tzinfo` on read, so a value stored as aware came back
  naive and compared unequal to a freshly built aware value. To keep reads and
  writes symmetric all timestamps are stored naive-but-UTC via
  `app.db.base.utcnow()`; callers that need tz-aware values localize on use.
- **Statuses are `String` columns, `StrEnum` is the source of truth.** The enums
  in `models.py` are Python-side; the DB stores plain text. This keeps the schema
  migration-free when a status list grows, avoids vendor-specific enum DDL, and
  still gives typed access in code. Validation happens at the repository/service
  boundary rather than in the database.
- **Payment "one active payment per user" is a partial unique index.**
  `CREATE UNIQUE INDEX ... ON payments(user_tg_id) WHERE status IN
  ('created','awaiting_proof','submitted')` (`sqlite_where=`). A plain unique
  constraint would also block historical `approved`/`rejected` rows, which must
  be allowed to accumulate; the partial index enforces the invariant ("at most
  one *open* payment") directly in the DB so it holds even under races.
- **Alembic runs in batch mode (`render_as_batch=True`).** SQLite cannot
  `ALTER` most column properties; batch mode recreates the table to apply
  changes. Enabling it globally means the autogenerated `0001_initial` and all
  future migrations stay SQLite-safe without hand-editing.
- **`fileConfig(..., disable_existing_loggers=False)` in `migrations/env.py`.**
  Alembic's default logging config disabled every already-configured logger,
  which silently muted the application's own loggers whenever a migration ran
  (e.g. at startup). Rerunning `fileConfig` with `disable_existing_loggers=False`
  makes migration logging additive and preserves app logging.
- **Startup migration runs off the event loop (`asyncio.to_thread`).** The async
  Alembic `env.py` calls `asyncio.run()` internally, which raises inside an
  already-running loop. The programmatic runner (`app/db/migrate.py`) is invoked
  from `app/app.py` via `asyncio.to_thread(upgrade_head)`, giving the migration
  its own loop on a worker thread.
- **`path_separator = os` in `alembic.ini`.** Silences the Python 3.12
  `Config.get_main_option` deprecation warning about the path separator when
  resolving `script_location`.
- **`render_item` hook auto-imports `JSONText`.** Autogenerated migrations that
  reference our custom `JSONText` column type need the import injected into the
  template; the `render_item` hook adds `from app.db.base import JSONText` so
  future `--autogenerate` revisions are importable without manual edits.
- **`BroadcastJob.text` is aliased `sa_text`.** The attribute name shadows
  SQLAlchemy's `sqlalchemy.text()` helper inside the module; the model imports it
  as `sa_text` to avoid the collision while keeping the public column name `text`.
- **`data/` is created at startup and git-ignored.** SQLite will not create a
  missing parent directory, so `ensure_sqlite_dir()` creates it before the engine
  connects; `data/` is added to `.gitignore` so the runtime DB is never committed.

## M0-04 — PanelGateway (pre-implementation safety rules)

These are binding constraints for the M0-04 implementation, not suggestions:

- **All panel access goes through one global `asyncio.Lock`.** Reads and writes share
  it; every write is wrapped in it and re-reads **bypassing the cache** to verify the
  change landed. A mismatch raises `PanelError` (no silent success).
- **Never call `api.login()`.** The panel is reached with token auth only
  (`AsyncApi(DOMAIN, token=VPN_TOKEN)`); the token must authenticate each request.
- **Read clients from `inbound.settings.clients`** (the 30 s cache builds the
  `{email: Client}` index from it); **never** use `api.client.get_by_email`, whose
  py3xui behaviour is the known mismatch.
- **Timeout and transport errors map to `PanelUnavailable`** (15 s default); they must
  never be surfaced as generic `PanelError`.
- **`restart_xray()` is never called automatically** and raises `NotSupportedError`
  ("Xray restart is not supported"); `download_panel_db()` is likewise never called by
  the gateway.
- **Scope of mutation:** outside explicit app flows, only `email="spike_test"` may be
  touched (smoke script); `ensure_client` returns an **existing** client unchanged.
### M0-04 — implementation

- **Clients are identified by `email == str(tg_id)`, never by `client.id`.** `Client.id`
  is the VLESS password/UUID and `uuid` may be absent (M0-03 notes), so the
  `{email: Client}` index built from `inbound.settings.clients` is the only lookup
  path. `get_client` is therefore O(1) from the 30 s cache.
- **`set_limits` passes `total_gb` through unchanged.** `py3xui.Client` has no validator
  converting GB↔bytes: `total_gb` is the raw wire value of `totalGB` (3x-ui's own unit,
  which the panel also counts in), while `total`/`up`/`down` are byte counters computed
  by the panel. The gateway therefore writes and verifies the number as given, and
  `get_traffic` exposes the raw values so callers decide how to label them. `None`
  means "unlimited" and is stored as `0` for both `total_gb` and `limit_ip`.
- **`reset_traffic` is an `update` with `up = down = 0`.** py3xui 0.7.0 offers no
  reliable reset wrapper; zeroing the counters through the normal verified write keeps a
  single write path (`total` and `expiry_time` are untouched).
- **One write primitive: `PanelGateway.mutate(apply, verify, desc)`.** Every write
  method (and `SubscriptionService.grant_days`) goes through it, so the read-modify-write
  runs under the global lock and the changed fields are re-read bypassing the cache.
  `apply` returning `False` means "nothing changes" (perpetual client) and skips the
  write entirely; `apply` returning `True` with a failing `verify` raises `PanelError`.
  This is what makes two concurrent `grant_days` add up instead of losing one.
- **`ensure_client` repeats the legacy add+update workaround and then checks it.**
  `client.add` stores `enable=True` even when asked for `False`
  (`handlers/start.py:52-55`), so the same object is immediately `update`d; afterwards
  the client is re-read and a still-enabled or `sub_id`-less client raises `PanelError`
  rather than being returned.
- **Perpetual clients are signalled, not written.** `grant_days` returns
  `GrantResult(changed=False, reason=UNLIMITED_REASON)` with
  `UNLIMITED_REASON = "клиент бессрочный"` so callers/UI can print the message verbatim.
- **`Container.init_panel()` owns construction.** The gateway (and the
  `SubscriptionService` built on it) is created once from `Settings` at startup and
  exposed as `c.panel` / `c.subscriptions`, so handlers never build `AsyncApi`
  themselves.
- **`tests/fakes.py::FakePanel` mirrors the gateway 1:1 (including `mutate`).** It is
  reused by later tasks; failure switches `unavailable` / `drop_writes` / `latency`
  cover the `PanelUnavailable` and verify-mismatch paths without a live panel.

### M0-06 — implementation

- **One matrix lives in `app/permissions.py`.** `Role`/`Permission` and the
  `owner ⊃ admin ⊃ support` presets (`ROLE_PERMISSIONS`) are the single source of
  truth; `permissions_for`/`role_has` are pure. `AdminService`/`Notifier` import
  these, never the reverse, so there is no import cycle.
- **`get_role` is async and delegate-based.** Owners are resolved from
  `settings.owner_ids` at construction time (env only); everyone else from the
  `admins` table (non-revoked rows). The plan's signatures
  (`get_role`/`has`/`staff_with`/`@require(perm)`/`check_callback(call, perm)`)
  are kept verbatim, but the acting bot and `AdminService` are injected once via
  `permissions.configure(...)` instead of being passed per call. This avoids
  importing the legacy `loads` singletons (which need a live `.env` at import
  time) and keeps the module unit-testable with fakes.
- **Cache = per-ID `admins` lookups only.** Owner status is stable at runtime, so
  it is never cached. `AdminService.invalidate(tg_id)` (or `invalidate()`) is the
  contract every future `admins` writer must call; a role change is effective on
  the next `get_role` after invalidation (test: `test_cache_invalidated_after_admins_write`).
- **`staff_with(perm, notify_flag)` returns a sorted, de-duplicated list** with
  owners always included; non-owner staff must additionally have the matching
  `admins.notify_*` column truthy. An unknown flag raises `ValueError` rather than
  silently matching nobody.
- **`require` denials:** a caller with **no** role is dropped *silently* (matching
  the legacy `ADMIN_IDS` early-returns); a **staff** caller lacking the specific
  permission gets a short `⛔ Недостаточно прав.` notice. Callbacks always re-check
  via `check_callback`, which answers `Недостаточно прав` with `show_alert=True`
  (hidden buttons are cosmetic only).
- **`Notifier` resolves recipients only.** `recipients_for`/`recipients_for_kind`
  map `CardKind`→`(permission, flag)` via `ROUTES`; delivery (`safe_send`, retries,
  `bot_blocked`) is M0-07. No I/O that sends lives here.
- **`/maintenance` moved from `main.py` to `handlers/legacy_commands.py`.** M0-01
  already relocated the legacy admin commands there, so M0-06.7's `handlers/main.py`
  path is realised in `legacy_commands.py`. The `/ban` "cannot ban an admin" guard
  now uses `get_role(target) is not None` (staff-vs-staff) instead of `ADMIN_IDS`.
- **Left for M0-07 (not ACL):** `handlers/payment.py` and `handlers/profile.py`
  still `for admin_id in ADMIN_IDS` to fan out error alerts — that is alert
  routing, not a membership check, and is ported to `Notifier` in M0-07.

### M0-05 — implementation

- **`SettingsService` owns the cache; writers must go through it.** Typed
  getters/setters cover the four §2.4 keys (`access_mode`, `maintenance_mode`,
  `bank_details`, `reminders_enabled`). Reads resolve cache → DB → default, and
  `set()` commits in its own short transaction *and* updates the cache, so a
  toggle is observable on the very next `get()` (B1). The cache is **TTL-bounded**
  (`CACHE_TTL = 20 s`, injectable via `ttl=`): once an entry expires it is re-read
  from the DB, so an out-of-band writer (the M0-11 CLI) is picked up within ~20 s
  without a restart. Trade-off: an *external* write can lag up to the TTL, while
  in-process writes are always immediate (test:
  `test_settings_cache_expires_and_picks_up_external_writes`).
- **`bank_details` env seed is a *default*, not a seed write.** §M0-05.2 calls it
  an "env seed"; `SettingsService` therefore falls back to
  `settings.bank_account_details` when the key is absent, while the actual
  idempotent DB seeding stays in the CLI (M0-11.5). No row is written by the
  service.
- **Context middleware never inserts (deviation from TASK_PLAN §M0-05).** TASK_PLAN
  says "upserts `users`"; PROGRESS §M0-05.3 refines this to update-only, because
  a bare update from a stranger must not create a row — that is the access-decision
  point moved into `/start` (M0-09.1). New repo helper
  `users.touch()` implements update-only; a stranger yields `None` and the
  middleware still sets `data["role"] = None`/`data["user"] = None`.
- **`data["role"]` is resolved through `AdminService`, not `permissions`.** The
  middleware holds the `Container` and calls `container.admins.get_role(...)`
  directly (same instance injected into `permissions.configure`), so the
  per-ID cache stays shared and consistent. Later middlewares read
  `data["role"]` (staff detection) instead of re-querying.
- **Throttle release + 30 s TTL.** Telebot runs `post_process` even after a
  handler exception (verified in `AsyncTeleBot._run_middlewares_and_handlers`),
  which fixes B10 for the exception path; the 30 s safety TTL (stale locks are
  ignored and replaced) is the backstop for any other leak. Duplicate/over-cap
  rejections return `CancelUpdate` *before* acquiring, so they never leak either.
  Cross-check with the reordering above: because Throttle is now last, a
  `CancelUpdate` from Maintenance/Access happens before Throttle is ever reached.
- **Duplicate vs over-cap.** A duplicate in-flight **callback** is answered
  `Подождите…` (`answer_callback_query`), a duplicate **message** is dropped
  silently. The rate cap (20 updates / 10 s, sliding window) drops silently.
  "Staff" is `data["role"] is not None`: exempt from the cap, **not** from the
  in-flight guard (§M0-05.5).
- **Legacy `BanMiddleware` is dropped now.** §M0-05.8 fixes the middleware set to
  Context/Throttle/Maintenance/Access (now registered Context → Maintenance →
  Access → Throttle), so the file-based `banned_users.json`
  gate from `middlewares.py` is removed from the runtime path. Until bans move to
  `users.status` (M0-09) + the real AccessMiddleware (M1-01) the Access
  placeholder only blocks `status == blocked`, i.e. DB-imported bans from M0-11.
  `middlewares.py` itself stays on disk (deleted in M0-09) but is no longer
  imported by `app/app.py`.
- **Middleware order is Context → Maintenance → Access → Throttle (revised).**
  §M0-05.8 originally listed Throttle second; it is moved **last** because telebot
  aborts the whole middleware chain (and skips `post_process` for *every*
  middleware) as soon as one returns `CancelUpdate`. With Throttle before
  Maintenance/Access, a cancelling gate would strand Throttle's in-flight lock and
  lock the user out until the TTL. Placing Throttle last means it only acquires a
  lock on updates that actually reach a handler, so those cancels can never leak.
  The 30 s TTL stays as a backstop for non-cancel leaks (cancelled task, shutdown
  mid-flight, a future middleware added after Throttle). Regression test:
  `test_cancel_by_maintenance_leaves_no_throttle_lock`.
- **`AccessMiddleware` null-guards `data["user"]`.** `ContextMiddleware` uses
  `users.touch()` (update-only), so `data["user"]` is `None` for a stranger; the
  access check is therefore `if user is not None and getattr(user, "status", None)
  == UserStatus.BLOCKED`. A missing/`None` user passes through and can never raise
  `AttributeError`/`KeyError` (test: `test_access_drops_blocked_user`).
- **`data` keys are produced by Context and consumed by later middlewares**
  (`role` → Throttle/Maintenance, `user` → Access). This is documented because
  the handler-port tasks (M0-09+) will also receive these keys via `data`.


## M0-07 — Notifier, text helpers, typed callbacks

- **`unpack()` normalises every parse failure to `InvalidCallback`.** The
  namespace dispatcher looks the payload up by its first segment and then calls
  the class's `parse()`, which raises `InvalidCallback` for a wrong segment
  count, unknown action/section or a non-int argument. Any stray
  `ValueError`/`TypeError`/`IndexError` is wrapped into `InvalidCallback` as a
  net, so handlers only ever need to catch one type regardless of how the data
  was edited (fixes B5).
- **The 64-byte guard raises `ValueError`, and measures UTF-8 bytes.** §M0-07.5
  requires an explicit `raise` (an `assert` disappears under `python -O`). The
  length is computed on `data.encode("utf-8")`, so a payload that fits in
  characters but not in bytes (Cyrillic text is 2 bytes/char) is still rejected.
- **`Confirmations` returns a result object, it does not raise.** `consume()`
  yields a `Confirmation` with a `ConfirmResult` status (`ok` / `expired` /
  `forbidden`) so handlers can choose their wording. Expired tokens are purged
  *before* lookup, so an unknown token and an expired token both read as
  `expired` — this deliberately does not distinguish them (no token-existence
  oracle to leak), and an owner/action mismatch is `forbidden` without burning
  the token. Tokens are `secrets.token_urlsafe(8)`; the alphabet never contains
  `:` so the token is safe to embed in callback data.
- **`_deliver()` is the one send path; `safe_send()` is a thin wrapper.** It
  returns `(delivered, message_id)` so `send_card()` can store the message id
  for later `sync_card()` edits; `safe_send()` keeps the public `bool` contract.
  Credentials/transport are never retried except the single 429 retry, and a
  blocked chat (403, or 400 with "chat not found"/"user not found"/"bot was
  blocked") flips `users.bot_blocked` through the new
  `db.repositories.users.set_bot_blocked` helper (a missing row is ignored —
  the chat id may belong to a stranger or a group).
- **`Notifier` keeps its M0-06 signature.** `bot` and `sessionmaker` are
  optional keyword arguments (plus `attach_bot()`), so `Notifier(admins)` — as
  built in M0-06 tests — still constructs a recipient-resolution-only instance
  and every sending method degrades gracefully (logs and returns `False`/`[]`)
  when unwired. `Container.init_rbac` passes the sessionmaker; `app.run()`
  calls `attach_bot(bot)` next to `permissions.configure` so the two enforcement
  paths share one bot.
- **`admin_cards` gained a tiny repository module.** `send_card()` records one
  row per delivered copy and `sync_card()` edits every row, re-sending and
  re-pointing the stored `message_id` when an edit fails (deleted message /
  stale token) — the §M0-07.3 "fallback to new message" requirement. Card
  bookkeeping is best-effort: a DB error is logged, never propagated into a
  send path.
- **The error-signature limiter lives with the notifier.** §M0-07.4/§M0-08.2
  both point at one implementation, so `Notifier.allow_error_alert(signature,
  window=600)` is it (M0-08's global handler will call it). It uses an
  injectable monotonic clock so the window can be tested without sleeping.
- **`pagination.nav_row()` returns plain `(label, data)` tuples.** The helper
  stays free of any `telebot` import so it can be unit-tested and reused by any
  keyboard builder; the caller owns the prev/next callback-data strings (and
  their namespace). `PAGE_SIZE = 8` per §M0-07.8; `paginate()` clamps the page
  index so first/last/out-of-range/single-page all behave.
- **`app/texts.py` is constants-only.** No formatting helpers, so it imports
  with zero side effects; the catalog is intentionally a skeleton (generic
  errors, confirm/cancel/back/next button labels, welcome, stale-button and
  expired-confirmation copy) — handler-specific copy is added as handlers are
  ported (M0-09+).
- **Dropped sub-task confirmed.** `TASK_PLAN.md` M0-07 still lists "Port
  existing admin-alert sites (`profile.py:28`, `payment.py:38`) to
  `Notifier.alert_staff(...)`"; PROGRESS §M0-07 marks it dropped because M0-09
  rewrites those handlers. Nothing in `handlers/` was touched here — the two
  legacy alert sites still fan out with the buggy legacy `bot.send_message`
  (unawaited, B2) until M0-09 replaces them, which is the point of the plan.
- **`retry_after` is capped, not honoured blindly (review follow-up).** A 429
  whose `retry_after` exceeds `MAX_RETRY_AFTER = 5 s` (Telegram can ask for ~60 s
  during a burst) makes that one send fail fast (`False`) with a warning instead
  of `await asyncio.sleep()`-ing inside the fan-out loop. Honouring an arbitrary
  delay in `safe_send` would stall the broadcast for *every* remaining
  recipient, which is exactly what B2 is about; a bounded pause keeps the loop
  responsive while still smoothing out brief rate limits. Test:
  `test_safe_send_gives_up_when_retry_after_exceeds_cap`.
- **`bot_blocked` bookkeeping is isolated and non-fatal (review follow-up).**
  `_mark_blocked()` opens its *own* short session/transaction (`async with
  sessionmaker() as session: … await session.commit()`) and wraps the whole
  thing — including the sessionmaker call — in `try/except` that only logs. A DB
  failure while flagging one unreachable user therefore cannot abort a fan-out
  for the other recipients. Test:
  `test_bot_blocked_bookkeeping_failure_does_not_abort_fan_out` (sessionmaker
  raises `RuntimeError`; the second recipient is still delivered).
- **Token byte budget is documented and bounded by a constant.** `cf:` payloads
  are the only variable-length ones, so `TOKEN_URLSAFE_BYTES = 8` is named
  explicitly and referenced from the module docstring; `token_urlsafe(8)` is 11
  chars, leaving ~50 bytes of headroom under the 64-**byte** limit. A regression
  test pins the arithmetic (`test_confirm_token_payload_stays_within_budget`) so
  a future longer token/namespace is caught here rather than at runtime.

## M0-08 — Audit service + global error handling

Scope: `TASK_PLAN.md` §3 M0-08 and `PROGRESS.md` §M0-08.1–§M0-08.4.

- **The reporting logic lives in `app/error_handler.py`, not in `app/app.py`.**
  PROGRESS lists `[app/app.py]` for M0-08.3, but an untestable `try/except`
  buried in `run()` cannot be covered by §M0-08.4's `tests/test_error_handler.py`.
  `app/app.py` now only *wires* it: it registers `ErrorReporterMiddleware` and
  calls `run_polling(bot, reporter)`. The AC (one log entry + ≤1 owner alert per
  window) is unchanged.
- **Handler exceptions are observed via a telebot middleware, not a polling
  hook.** Verified against the installed telebot: `AsyncTeleBot.polling()` has no
  `exception_handler` parameter (unlike the sync client), telebot logs a handler
  exception itself and then **swallows** it, so `post_process(update, data,
  exception)` is the *only* place it can still be seen. `run_polling` therefore
  only covers failures of the long-poll loop itself (network/auth), where it
  reports and **re-raises** so the process supervisor still restarts the bot.
  The middleware is registered *after* the four §M0-05 gates so
  `build_middlewares`' tested order (and `test_build_middlewares_order`) is
  untouched.
- **One signature, two error sites = two alerts.** `error_signature()` uses the
  *innermost* traceback frame as `module:function:line`, i.e. the raise site, so
  two different bugs never share a signature and the same bug never floods the
  owners. The 10-minute limiter itself stays where M0-07.4 put it
  (`Notifier.allow_error_alert`) — M0-08 adds no second implementation, which is
  exactly what M0-08.2 asks for; `notifier.py` is unchanged.
- **Alerts go to `kind="alert"` (owners + `server.view`), as `ROUTES` already
  said in M0-07.** Owners are always included; an `admin` holding `server.view`
  also sees bot-health alerts. Kept consistent with the M0-07 routing table
  rather than inventing an owner-only channel.
- **Audit `actor_tg_id`/`actor_role` are `NOT NULL`, so they get sentinels
  instead of nullable writes.** `AuditService.log(None, ...)` writes
  `SYSTEM_ACTOR = 0` (no human triggered it: jobs, timers, startup) and an empty
  role unless the caller passes `role=`. `target_id` is coerced with `str()`
  because the column is `String(64)`.
- **`log()` returns `bool` and never raises.** Auditing is a side effect of an
  action that already happened; §0.1 rule 6/7 want no side effect to take a
  handler down. `False` means "not written" and callers may ignore it.
- **`Container.init_audit()` is a separate initializer** (like `init_rbac` /
  `init_settings`) so M0-09 handlers can reach it as `c.audit` without changing
  the existing `init_rbac()` contract.
- **Tracebacks are masked, and so is the alert text (§0.1 rule 6).** The
  formatter renders `exc_text` *after* logging filters have run, so
  `SecretMaskingFilter` now pre-renders `exc_info` and masks it — otherwise a
  token quoted in an exception message would reach stdout. For the same reason
  `ErrorReporter` masks the exception text before it goes into the owner alert,
  reusing the extracted `mask_secrets()`/`normalize_secrets()` helpers (one
  masking rule for logs *and* alerts). Alert text is then `esc()`-escaped, since
  it is sent with `parse_mode="HTML"`.
- **Not covered here (deliberately):** §M0-09 will port the handlers; the global
  handler currently reports *any* handler exception, and per-handler
  domain-error answers (`PanelUnavailable` → friendly reply) arrive with those
  ports. `AuditService` has no UI yet — `audit.view` screens land in M1.

### M0-08 — review follow-up (two edge cases)

- **`CancelUpdate` is control flow, not a failure.** `ErrorReporterMiddleware`
  returns early on `CancelUpdate`, the sentinel the §M0-05 gates return to drop
  an update. Note what the installed telebot actually does (verified): a
  *middleware* returning `CancelUpdate` makes telebot skip `post_process`
  entirely, and `CancelUpdate` is a plain class (`class CancelUpdate: ...`), so
  it is **not** a `BaseException` and cannot even be `raise`d. The guard is
  therefore defensive/future-proof (and protects any future gate that raises
  instead of returning), not a fix for a live alert storm. The middleware's
  `exception` parameter is annotated `Any` for that reason — telebot hands over
  a non-exception object here.
- **`error_signature()` = `Type:module:function:line`, preferring the innermost
  `app/` frame.** Including the exception type plus the *application* caller
  stops two unrelated bugs from sharing one signature when both surface inside
  one shared library frame (`json.loads`, SQLAlchemy `execute`, `httpx`) — a
  collision would make the 10-minute limiter swallow the second alert. Application
  frames are detected by module name (`app.…`) or filename (`/app/`), and the
  absolute innermost frame is the fallback when no application frame exists.
  Known limitation, measured: `pydantic.ValidationError` is re-raised from
  pydantic's own code and carries **no** application frame at all, so two
  `Settings` validation failures still share `ValidationError:pydantic.main:__init__:N`
  — acceptable because settings validation fails once at startup (before
  polling), not per update.

## M0-09 — Port start / profile / support / broadcast / ban onto services

Scope: `TASK_PLAN.md` §M0-09 and `PROGRESS.md` §M0-09.1–§M0-09.7.

- **Handlers are plain functions; the telebot wrapper is a one-liner.** Every
  ported module exposes `async def <cmd>_command(message, bot, container)` next
  to `register_<cmd>_handler(bot, container)`. §M0-09.7 asks for handler tests
  without a live poller; a closure created inside `register_*` could not be
  called directly, so the logic lives at module level and the registered callback
  only forwards (it is excluded from coverage with `# pragma: no cover`). The
  FSM-dependent support handlers therefore need only `get_state`/`set_state`/
  `delete_state`/`retrieve_data`, which `tests/fakes.py:FakeBot` now implements.
- **`/start`'s insert lives in `UserService.register`, not in the handler.**
  §M0-09.1 says "insert here" and §0.1 rule 3 bans business logic in handlers.
  `users_repo.upsert_from_telegram` + `set_status(APPROVED)` run first (so the
  row survives a later panel failure, which the AC asserts), then
  `get_client` decides returning-vs-new and `ensure_client` runs only for a new
  user. `panel_client_uuid` is stored best-effort: a DB hiccup there logs a
  warning instead of failing a `/start` that already succeeded at the panel.
- **A panel outage is answered, never raised out of a handler.** `register`,
  `/profile` and the ban commands treat `PanelError` (the domain error the
  gateway raises) as an expected condition: friendly reply to the caller plus a
  rate-limited staff alert (§0.1 rule 7, §M0-09.1's "always reply"). Unexpected
  exceptions still propagate to M0-08's `ErrorReporterMiddleware`.
  Deliberate deviation from rule 7's letter for ban/unban: the DB state change is
  written **first** and the panel write is best-effort, reported through
  `AccessChange.panel_error`; raising instead would leave an admin with no answer
  about a ban that *did* take effect. The warning is rendered in the reply
  (`PANEL_WARNING`) and alerting is duplicated through `alert_staff`.
- **Block semantics.** `/ban` = `status='blocked'` + `set_enabled(False)`;
  `/unban` = `status='approved'` + `set_enabled(True)` only when the panel expiry
  is in the future. `expiry_ms == 0` (the panel's unlimited marker) counts as
  "in the future", otherwise an unlimited client could never be re-enabled. An
  expired subscription stays disabled and the admin is told so
  (`UNBAN_EXPIRED`, §0.2). A blocked user with no panel client just gets the
  status change — `_client_present` distinguishes "known absent" (skip the
  panel) from "read failed" (attempt the write and surface the error).
- **`/maintenance` was ported out of `handlers/legacy_commands.py`** even though
  §M0-09 does not list it. §M0-09.6 requires the runtime path to stop importing
  `config`/`loads`, and `legacy_commands.py` was the last user of those singletons
  for admin commands; keeping it alive for one 15-line command would have been
  worse. It also **fixes B1**: the legacy toggle mutated the import-time
  `config.IS_MAINTENANCE_MODE` constant that `MaintenanceMiddleware` never reads,
  so it had no effect. `maintenance_command` now calls
  `SettingsService.set_maintenance_mode` (what the middleware reads) and writes a
  `setting.set` audit row. The two empty `pass` placeholders in that file
  (`/list`, `/profile_of_user`, M2-02/03) were dropped with it.
- **`/pay` stays legacy.** Moving it would be M0-10's job (it needs the payments
  service). `handlers/__init__.py` now exports only `register_payment_handler`
  and `app/app.py` calls it explicitly next to `register_all_handlers(bot,
  container)`, so `app/handlers/**` imports neither `config` nor `loads` — the
  §M0-09.6 criterion is pinned by
  `tests/test_handlers_maintenance.py::test_handler_package_does_not_import_the_legacy_modules`
  (a fresh interpreter asserts the modules are absent from `sys.modules`).
  `middlewares.py` (the legacy ban middleware reading the JSON file) was deleted
  with the banned-file logic; nothing imported it any more.
- **Broadcast recipients come from the DB, pacing stays.** `approved` and
  `bot_blocked = false` (§M0-09.4). The 0.1 s sleep is a module constant
  (`broadcast.PACING`) so tests can zero it via monkeypatch; the summary is built

- **`/ban`'s staff check reuses `permissions.get_role`.** The legacy guard read a

  any write, and an unknown target (no `users` row) gets `ERROR_UNKNOWN_USER`
  instead of a silent no-op.

### M0-09 — review follow-up (three edge cases)

- **`/start` only promotes the row it creates.** `UserService.register` now asks
  `users_repo.get` first and calls `set_status(APPROVED)` **only** when the row did
  not exist. The previous "if `status != approved` → set approved" form would have
  overwritten an administrative state (`pending`/`rejected`, or `blocked` for a
  user whose update slipped past the access gate) on every `/start`, which the
  M1 invite/approval flow would have to fight. `upsert_from_telegram` still
  refreshes `username`/`first_name`/`last_seen_at` and clears `bot_blocked` for an
  existing row — that is the part `/start` is supposed to update. The two queries
  run in one transaction, and the `new → approved` promotion keeps §M0-09.1's
  "row created with `approved`" acceptance criterion true for new users.
- **`/unban` can retry a failed panel call.** A panel outage during `/unban` left
  the DB at `approved` and the panel client disabled; the next `/unban` used to
  answer "Этот пользователь не забанен" and nothing could clear that state short
  of re-banning. The handler now proceeds when the status is `blocked` **or** when
  `UserService.needs_panel_retry()` reports a disabled client. That probe returns
  `True` for a disabled client *and* for an unreadable panel (so the retry attempt
  surfaces the real error through `AccessChange.panel_error`); it returns `False`
  only when the panel is reachable and the client is absent or already enabled, so
  the "not banned" answer is preserved for a genuine non-ban. No second condition
  reads `users.status` — `needs_panel_retry` is the single place that knows the
  panel side of the state machine.
- **`_traffic` distinguishes "no client" from "read failed".** It used to return
  `None` for both, which made `/unban` silently do nothing when the panel was
  unreachable. It now returns a `(traffic, error)` pair: `(None, None)` = the panel
  genuinely has no client (nothing to enable), `(None, msg)` = the read failed, so
  `unban` leaves the client untouched (the expiry is unknown — re-enabling an
  expired subscription would be wrong) and reports `panel_error`, which the handler
  renders as `PANEL_WARNING` plus a staff alert.
- **The broadcast never holds a DB session while pacing.** `users_repo.list_broadcast_ids`
  selects only `tg_id` and materialises `int`s *inside* the session, and
  `UserService.broadcast_targets` closes that session before returning. The send
  loop therefore sleeps 0.1 s per recipient with no session — and no connection —
  checked out, which a 10k-user broadcast would otherwise starve (the pool is
  small by design). Selecting a full `User` row was the risk: iterating detached
  instances invites a lazy load per attribute after the session is gone.
  `tests/test_handlers_support_broadcast_ban.py::test_broadcast_holds_no_db_session_while_pacing`
  pins this with a sessionmaker proxy that counts open sessions and records the
  count at every send *and* every sleep.

## M0-10 — Payments rewrite (DB-backed, atomic)

- **The state machine lives in the `payments` row, not in the FSM.** The legacy
  `handlers/payment.py` kept the in-progress payment in `UserStates` and re-read
  `config.RATES` on every step, so a restart between "Готово" and the admin's
  decision lost the whole flow and an old admin card pointed at nothing. M0-10
  deletes that handler (and the now-empty top-level `handlers/` package) and
  makes `payments` the single source of truth: `submit` writes `awaiting_proof`
  and fans the card out; `approve`/`decline`/`cancel` (and the stale sweep) are
  the only transitions.
- **Every transition is an atomic claim, not a read-modify-write.**
  `payments_repo.claim` runs a single `UPDATE ... WHERE id=:id AND status=:from`
  and treats `rowcount == 1` as "I won". Two admins pressing **Одобрить** at the
  same instant therefore apply the subscription exactly once — the loser sees
  `rowcount == 0` and gets `AlreadyProcessed` ("уже обработано"). Testing a
  read-then-check would have been a false guarantee, so `claim` never reads the
  row first.
- **A panel failure never reverts — it is retried idempotently.** `approve`
  claims first (so the admin action is recorded and de-duplicated), then applies
  via `SubscriptionService`. Reverting to `submitted` on `PanelError` would
  re-grant the days if the panel had actually processed the write before the
  response was lost, so instead the row stays `approved` with `applied_at IS
  NULL` and every card is re-rendered with a **«Повторить применение»**
  (`pay:retry:<id>`) button. To make the retry safe, `_apply` persists the
  intended expiry (`expiry_after_ms`, computed via `calculate_expiry_ms`)
  *before* the panel write and then sets that exact target (not `grant_days`);
  a retry compares the live expiry against the recorded target and skips a
  second grant when `current >= target`. Only a successful apply sets
  `applied_at`, which is also what the startup reconcile looks for.
- **`awaiting_proof` is the pending state; `submitted` means "receipt in hand".**
  Pressing «Готово» moves `created → awaiting_proof` and fans the review card out
  immediately (review never waits for the optional receipt). An uploaded
  photo/document is routed by an explicit DB read (`get_pending_for_user`):
  a pending payment gets `receipt_file_id`/`receipt_kind` and is promoted to
  `submitted`, and the file is forwarded under every staff card as a reply;
  otherwise the user's media goes to support (when they are in the
  `waiting_for_help` state) or gets a short hint. Admin decisions claim from
  `PENDING_STATUSES` (`awaiting_proof` **or** `submitted`) so both are decidable.
- **Unreviewed payments expire, and the user can always cancel.** A pending
  payment older than 24h is moved to `expired` by the startup sweep
  (`expire_stale`, run inside `reconcile_payments`) and the user is told so;
  the "Отмена" button cancels a `created`/`awaiting_proof`/`submitted` payment
  directly. Together they stop an unresponsive admin from soft-locking a user
  out of free-text interaction (`has_pending`) forever.
- **The unlimited case is "enable but never shorten".** `grant_days` already
  returns "not changed / unlimited" for a perpetual client (`expiry_time == 0`);
  the payment simply enables the client and stores `expiry_before ==
  expiry_after == 0` rather than inventing a finite expiry. The review card also
  carries an explicit warning so the admin is not surprised that pressing
  "Одобрить" adds no days.
- **Reconcile is idempotent, not a migration.** Startup lists
  `approved AND applied_at IS NULL`, alerts the owners with a
  `pay:retry:<id>` button, and `apply_approved` re-checks the state before
  applying (returns `False` when already applied/not approved). Pressing retry
  twice, or restarting twice, applies the days once.
- **The pending notice reads the DB, never the FSM.** The old flow blocked
  free-text while a payment was pending via `state=UserStates.pending_confirmation`;
  M0-10's replacement is a `has_pending(tg_id)` query guarded to skip commands,
  so `/profile` & co. still work and no handler consults FSM state for payments.
- **The card is a `Notifier` card, so it survives restarts and syncs on every
  copy.** `submit` uses `notifier.send_card(CardKind.PAYMENT, ...)`, which stores
  one `admin_cards` row per delivered `message_id`; `approve`/`decline`/`cancel`
  call `notifier.sync_card(...)`, so all admins see the final state even after a
  process restart. `Notifier` also keeps "safe send" semantics — a deleted chat
  never breaks a decision.

## Legacy-import hardening (bug-fix pass on M0-09 / M0-10 / M0-11)

- **"Unlimited" now requires `enable=True`.** The legacy world created clients with
  `enable=False` **and** `expiry_time=0`, so the old reading of `expiry == 0` as
  "lifetime" turned every one of them into a free permanent subscription the moment
  a payment was approved or `/unban` ran. `subscriptions.is_unlimited(expiry, enabled)`
  is now the single predicate (`expiry == 0 and enabled`), and
  `subscriptions.base_expiry_ms(expiry, enabled, now)` normalises the arithmetic:
  an unset expiry on a **disabled** client (or an unknown `None`) counts from `now`,
  so a grant produces a finite date instead of `0`. `calculate_expiry_ms` is
  deliberately unchanged (`0 → 0`) — it only ever sees a *normalised* value.
- **A never-activated client is pinned, not re-enabled.** `/unban` re-enables only a
  genuinely perpetual client (unset expiry **and** enabled) or a future expiry.
  Otherwise it writes `expiry_time = now` (best effort, reported as
  `panel_error`), keeps the client disabled and answers `UNBAN_EXPIRED` — the
  subscription is over, only bot access came back. This is the only place that
  mutates the panel from the ban flow beyond `set_enabled`.
- **The payment card no longer claims "бессрочно" for a placeholder.**
  `PaymentService._current_expiry` returns the *effective* expiry: `0` only for a
  truly perpetual client, `now` for a placeholder, so the review card shows a date
  and the "unlimited" warning only fires when it is real.
- **One importer, two entry points.** `app/services/legacy_import.LegacyImporter`
  backs both `python -m app.cli import-legacy [--dry-run]` and the startup hook, so
  a manual and an automatic import cannot drift. It is idempotent (second run
  refreshes, creates nothing), imports every numeric-`email` panel client as an
  `approved` user (`panel_client_uuid` set, `@username` parsed from `comment`),
  turns `banned_users.json` ids into `blocked` + a disabled client, pins the
  placeholders to `now`, and seeds `settings.bank_details` from
  `BANK_ACCOUNT_DETAILS` once.
- **Startup refuses to run blind.** `app.app.ensure_legacy_import` compares the
  `users` row count with the panel's numeric clients after the panel is built:
  non-empty DB → no-op; empty DB **and** no panel clients → normal fresh start;
  empty DB **and** clients → run the import when `AUTO_IMPORT_LEGACY=true`,
  otherwise raise a `RuntimeError` naming the exact command. An unreachable panel
  only logs a warning: a transport failure is not proof of an empty deployment.
  Rationale: after M0-09 `/broadcast`, `/ban` and `/pay` read only the DB, so an
  un-imported deployment silently reached nobody, could not ban and would hit the
  `payments → users` foreign key.
- **`/pay` guards the foreign key in the service, not in the handler.**
  `payments.user_tg_id` is an FK into `users`; `PaymentService.create` raises the new
  `NotRegistered` domain error when the row is missing, and the `pay:sel` callback
  answers `PAYMENT_NO_ACCOUNT`. (`/pay` itself already refuses a non-`approved`
  caller, so this only closes crafted/stale callbacks.)
- **`README.md` documents the migration as step zero.** The import warning is the
  first section of the file (before setup), because forgetting it is invisible at
  startup and only shows up as "unknown user", silent broadcasts and a broken
  `/pay`.
- **Not done on purpose:** the CLI has no `migrate`/`backup` subcommands and there is
  no `Dockerfile`/compose yet; those remain M0-11 scope and are unrelated to these
  two bugs.

## S0-1 — Expiry semantics (legacy `0` placeholder)

- **`0` is perpetual only while the client is enabled.** `calculate_expiry_ms` now
  takes `enabled` and owns the whole rule (S0-1.1): `0` + enabled → `0` (never
  modified); `0` + disabled, negative (the panel's "start on first use" marker) or
  `None` → `now + days` (a never-activated client counts from now); `>0` → extend
  from `max(old, now)`. The intermediate `base_expiry_ms` helper is retired — every
  caller passes the raw panel expiry plus `enabled` directly, so there is one place
  to reason about the placeholder.
- **`grant_days` no longer early-outs.** The old `is_unlimited(...)` guard ran
  *before* normalisation, so a `0` + disabled client skipped the grant entirely and
  stayed a free permanent subscription. It now calls `calculate_expiry_ms` with
  `enabled` and treats a returned `0` as "no write" (`UNLIMITED_REASON`), which only
  happens for a genuinely perpetual client.
- **`_apply` uses the pre-freeze `enabled`.** The payment path reads the client's
  `enable` flag **before** `freeze(...)` switches it on and feeds that value to
  `calculate_expiry_ms`; a placeholder therefore gets `now + days` while a truly
  unlimited client is still enabled-but-not-shortened.
- **The review card distinguishes three states.** `_current_expiry` returns `0`
  only for a truly unlimited client, the new `NOT_ACTIVATED_MS = -1` sentinel for a
  `0` + disabled placeholder, and a real timestamp otherwise. `_expiry_label`
  renders the sentinel as «не активирован», so the card never shows a false finite
  date and the «бессрочно» warning only fires when it is real.
- **`/profile` mirrors the rule.** `PROFILE_NOT_ACTIVATED = "не активирован"` is
  shown for a disabled `0` client; only an enabled `0` renders «Бессрочно».
  *(S1-1 replaced this card with the dashboard and renamed the strings to
  `PROFILE_STATE_NOT_ACTIVATED` / `PROFILE_UNLIMITED = "∞"` — see §S1-1.)*
- **`/unban` no longer writes the expiry.** It re-enables the panel client only when
  `expiry_ms > now` and leaves the expiry untouched. The old "pin `0` to `now`"
  branch is gone: it would have turned a banned unlimited client (`0` + now disabled)
  into a permanently expired one. A `0`/expired client stays disabled and the admin
  gets the existing `UNBAN_EXPIRED` reply ("доступ … до оплаты").
- **Import hardening.** `_normalize_client` pins `0` + disabled → `now` and now
  asserts a `0` + enabled (perpetual) client is left untouched (S0-1.8).

## S0-2 — Traffic data, units, reset

- **`totalGB` is bytes — but that is an assumption, not a verified fact.** The
  panel's `totalGB` field is treated as **bytes** (S0-2.1), with one knob:
  `PANEL_TOTAL_UNIT_BYTES = 1` in `app/services/panel.py`. `gb_to_bytes()` is the
  only way in (admins think in GB) and `_to_panel_total()` the only way out, so
  flipping the knob to `1024**3` is a one-line change. `bytes_to_gb` was
  deliberately **not** added: nothing needs it (the panel UI is the GB view).
  Recorded in `docs/panel_api_notes.md` as **"unit unverified (bytes assumed)"** —
  the live smoke run (`scripts/smoke_panel.py`, S0-2.8) is what settles it.
- **One inbound read, two indexes.** `_read_clients` became `_read_snapshot`: a
  single `inbound.get_by_id` now yields both `settings.clients` and
  `client_stats`, and the cache stores the pair (`_clients` + `_stats`), so the
  two can never disagree or be half-refreshed. `_invalidate()` clears both.
- **Merge precedence (S0-2.3).** `up`/`down`/`last_online` come from
  `client_stats`; `total`/`expiry_ms`/`enable` from the settings client. A client
  with no stats entry silently falls back to the settings copy, and the
  `client_stats` list being absent (empty `getattr` result) is not an error.
- **`last_online_ms` is always `None` today.** `py3xui`'s `Client` model has **no**
  last-online field, so the panel's value (if any) is dropped before we see it.
  The field is optional (`ClientTraffic.last_online_ms: int | None = None`) and
  `_last_online_ms()` probes the plausible names, so it starts working the day a
  library/route exposes one — without pretending we have data we do not have.
- **`reset_traffic` uses the panel's dedicated route, verified against the stats.**
  `py3xui 0.7.0` *does* wrap it: `client.reset_stats(inbound_id, email)`
  (`/panel/api/clients/resetTraffic/{email}`) — preferred. Otherwise the raw route
  from the task is used: `POST {domain}/panel/api/inbounds/{id}/resetClientTraffic/{email}`
  with `Authorization: Bearer <vpn_token>`, built from `settings.domain` with
  `rstrip("/")` so a panel behind a base path keeps it (S0-2.5). `httpx` was
  already a direct dependency, so no requirements change.
  - **Rejected:** `inbound.reset_client_stats(inbound_id)` — it resets **every**
    client of the inbound, i.e. one user's reset would wipe all counters.
  - **Rejected:** the old "read, set `up=down=0`, `update`" fallback — it writes a
    field the panel does not read back, so it "succeeds" while doing nothing.
  - The call runs **inside `_lock`** (a write), is followed by `_invalidate()`,
    and is then **verified by re-reading the stats** (`up == down == 0`). Verifying
    against the returned settings client would be a no-op: its own `up`/`down` are
    already stale/zero, which is exactly why the merge exists.
  - The return value stays a `Client` (signature unchanged) — the settings client.
- **`set_limits` now takes bytes** (`total_bytes=`, not `total_gb=`) and writes
  `client.total_gb = _to_panel_total(total_bytes)`; `None` still means unlimited.
  No caller in `app/` passes GB, and none existed before either (the method was
  only reached from tests), so nothing else needed porting.
- **`FakePanel` mirrors the real split.** `tests/fakes.py` keeps `_stats` separate
  from `_clients`, so `get_traffic` merges and `reset_traffic` zeroes exactly what
  the real gateway does (S0-2.6). A fake that stored one object would have made
  the new tests pass without exercising the merge at all.
- **`scripts/smoke_panel.py` (S0-2.8) was created, not run.** The agent has no
  access to the live panel and no `VPN_TOKEN`, so the script is operator-gated: it

## S1-1 — Profile dashboard

- **State order is expiry-first, and there are six states, not four.** The panel
  disables a client the moment its expiry passes, so `enable=False` alone cannot
  mean "never paid". `profile_state` therefore checks, in order: disabled + `0` →
  `not_activated`; disabled + future expiry → `suspended` (paid, then frozen);
  disabled + past expiry → `expired`; enabled + `0` → `unlimited`; enabled with
  `≤ 3 d` left → `expiring`; otherwise `active`. Naming the states (instead of
  inlining the branches inside `render_profile`) makes each AC branch assertable on
  its own and keeps `render_profile` a pure formatter.
- **`render_profile` builds its own keyboard.** The planned signature is
  `render_profile(info, now, *, link, timezone) -> (text, Any)`, so it calls
  `profile_keyboard()` and returns the pair. `now_ms` is a **parameter**, not a
  clock read, so the expiry and activity lines share one "now" and every state is
  reachable in a test without freezing time. `profile_command`/`profile_callback`
  call `app.ui`'s `_now_ms()` once per reply.
- **`∞` is deliberately reused for two different fields.** `PROFILE_UNLIMITED =
  "∞"` renders both the expiry (`📅 До: ∞`) and the traffic denominator
  (`0 Б / ∞`) — "no limit" in both cases, which is exactly what the panel's `0`
  means. A never-activated client still shows `0 Б / ∞` in the traffic line, so the
  S1-1.13 test distinguishes it from an unlimited one by asserting on the *expiry*
  line (`📅 До: ∞`) rather than on the whole card.
- **`load_profile_info` never sends anything — the caller does the alert.** The AC
  ("never sends, never raises; the caller owns the reply") is taken literally: the
  `PanelError` is logged there and the friendly text returned, while
  `profile_command` / `profile_callback` do the `alert_staff`. The trade-off is
  that the staff alert now carries the friendly copy instead of `str(exc)`; the
  full exception stays in the log (`logger.warning`), which is where it is
  actionable. The old B4 behaviour (friendly reply **and** a staff alert) is
  preserved — the existing outage test still asserts exactly one owner message.
- **`bar` is omitted, not zero-filled, when there is no quota.** `total == 0` means
  "no traffic limit", so a full or empty bar would be a lie; the line collapses to
  `📊 Трафик: 0 Б / ∞` (`TASK_PLAN.md` §S1-1.9: "bar omitted when `total == 0`").
- **"message is not modified" is matched by substring, not by an API class.**
  `app.ui.edit_or_send` inspects `str(exc).lower()` because telebot surfaces the
  `400` as a plain `ApiTelegramException` whose text is the only stable signal.
  Treating it as success is what stops a `prf:profile` re-render from posting a
  duplicate card.
- **`sub_url` lives in `app/utils/text.py` with a `TYPE_CHECKING` import.** It is
  the single place a link is built (§S1-1.6), so `app.settings.Settings` is imported
  only for typing — `app/utils/text.py` stays a zero-dependency leaf module.
- **`FakeBot` grew an edit/delete slice, which changed exactly one payment test.**
  `tests/fakes.py` now implements `edit_message_text` (including the Telegram
  "not modified" `400`) and `delete_message`, because S1-1.4/.5 cannot be tested
  without them. `tests/test_payments.py::test_user_cancels_pending_payment_via_callback`
  had been relying on `edit_message_text` being **absent** (the old fake raised
  `AttributeError`, so `payment._edit` fell back to `send_message`); its assertion
  now accepts either the edit or the send. **No production code changed for this.**
- **`ProfileNav.SECTIONS` declares the QR / instruction / link tokens already.**
  Their screens land in S1-2…S1-5, but the namespace is validated against a
  `frozenset`, so adding a token later would be a silent behaviour change for
  `unpack`. Declaring them with the dashboard keeps `unpack(pack)` a round-trip for
  every button that is already on screen and lets the S1-1.10 keyboard be verified
  in tests.
- **The old `profile_text` helper is deleted, not deprecated.** It was only reached
  from `profile_command` and its own tests; leaving it would have kept two renderers
  (and the removed `PROFILE_STATUS_*` / `PROFILE_LINK_*` strings) alive. The
  `/profile` block in `app/texts.py` now carries the dashboard catalog, including
  the five keyboard labels.
  *(The pre-declared `ProfileNav` tokens and the placeholder `prf:` payloads in the
  S1-1 tests were resolved by S1-2/S1-3 — and by S1-4 for `prf:pay` / `prf:support`,
  which the `profile_keyboard()` card already advertised. See below.)*

## S1-2 + S1-3 — QR, instructions and link screens

- **`profile_callback` is a `prf:` dispatcher, not one long `if`.** S1-2 and S1-3 add
  four screens to the one that existed, and every one of them needs the *same*
  plumbing: a panel read, the "no client → run `/start`" branch, the outage text plus
  a staff alert, the stale-QR-photo cleanup and `answer_callback_query` (B5). That is
  `_resolve_target` + `_reply_screen`; a screen supplies only `build(snapshot, link)`.
  The refactor is inside the task's own scope — without it, each new button handler
  would have copied the B5 guard four times, which is exactly how a spinner gets left
  running on the fifth screen someone adds later.
- **QR is the only screen that sends a new message instead of editing.** Telegram has
  no "turn this text message into a photo" edit, so `_show_qr` must `send_photo`. The
  shared `delete_if_photo` still runs first (inside `_resolve_target`), so pressing
  📱 twice replaces the photo instead of stacking two; the dashboard text card is left
  above it, which keeps `⬅️ Назад` (`prf:profile`) meaningful.
- **The PNG is rendered into a `BytesIO`, never a file.** `send_photo` accepts a
  file-like object, and the container filesystem may be read-only — a temp file would
  also leave the subscription URL on disk. The buffer is `seek(0)`-ed and given
  `name = "qr.png"` because telebot derives the multipart upload filename from that
  attribute. Rendering is **deterministic** (segno writes no timestamp chunk), which
  is what the §S1-2.1 "identical URL → identical bytes" AC actually checks.
- **The scan quality AC is verified structurally, not by decoding.** No QR *decoder* is
  a dependency of this project (only the `segno` encoder), so the literal "a phone
  camera scans to the exact sub URL" stays a manual/operator check — it is documented
  as such in `PROGRESS.md`. What the build *does* pin is the geometry: the test
  asserts the PNG signature and determinism, and (checked during development) the
  `IHDR` size equals `segno`'s `symbol_size(scale=10, border=3)` for the same payload
  (350×350, version 3, for the example URL), so the scale/border/colour parameters
  really do reach the file.
- **Instruction copy is substituted with `str.replace`, not `.format`.** §S1-3.3 asks
  for `replace` and the reason is durability: the operator retypes this prose, and a
  stray `{` in a hand-edited string would raise `KeyError` *at render time* — inside a
  callback handler, with the button already spinning. `replace("{link}", esc(link))`
  cannot fail that way, and the value is escaped because the message is `HTML`.
- **No URL is hard-coded in the catalogue — not even a client's website.** The link is
  always `sub_url(settings, snapshot.sub_id)`, i.e. the caller's own. The Windows/macOS
  steps say "скачайте Hiddify с официального сайта" rather than naming a domain, so the
  "no literal URL" AC can be asserted mechanically (`"{link}" in template` **and**
  `"http" not in template`) without carving out an exception. `INSTRUCTION_PLATFORMS`
  is the single ordered source shared by `INSTRUCTIONS`, `INSTR_PLATFORM_LABELS` and
  the picker's button order.
- **The picker is static, so it works during a panel outage.** `prf:instr` renders from
  constants only — no `get_traffic` call, no link — while the *platform* screens need
  the link and therefore show the outage text (and alert staff) like the dashboard.
  That keeps one useful screen reachable when the panel is down.
- **`⬅️ Назад` on a platform screen returns to the picker.** The picker
  (`prf:instr`) is the parent of the four platform screens, so back means "one level
  up", not "all the way out"; only the picker's own `Назад` and the link screen's go to
  `prf:profile`. This is asserted as a round-trip (dashboard → picker → Android → back
  → picker) rather than by comparing strings.
- **An unknown platform is still guarded, even though `unpack` already rejects it.**
  `prf:instr_bsd` never reaches the branch: `instr_bsd` is not in `ProfileNav.SECTIONS`,
  so the stale toast comes from `unpack` (and that is now the crafted-payload test case
  that replaced `prf:qr`). The `texts.INSTRUCTIONS.get(...)` guard stays anyway, because
  adding a platform means editing `app/texts.py`, and a catalogue/namespace drift would
  otherwise be a `KeyError` inside a handler. It is unit-tested directly, and a
  parametrized `ProfileNav(f"instr_{platform}")` round-trip over
  `texts.INSTRUCTION_PLATFORMS` makes the drift loud.
- **`FakeBot.send_photo` / `send_document` now keep the object instead of `str(...)`.**
  The §S1-2.2 AC is "`send_photo` gets a `BytesIO`", which a stringified fake cannot
  show. Only `tests/test_payments.py` reads `.media`, and it reads the chat id, so no
  other test changed.

## S1-4 — Start menu, `/help`, pay/support entry

- **`show_tariffs` / `enter_support` absorbed the *whole* command body, guards
  included — not just the "render the screen" tail.** §S1-4.1/4.2 only spell out the
  signature, but extracting less would have made `prf:pay` a second, *less*-guarded
  door into the payment flow: the approval check, the panel read and the outage
  branch (with its staff alert) all had to move, or a pending user pressing 💳 would

  share one path" is literally true and cannot drift. The import direction is

  `edit_or_send(bot, chat_id, None, …)` is exactly `reply()` — a fresh

## S1-5 — Link regeneration and post-payment polish

- **The central `cf:` dispatcher learns the action with a new, additive
  `Confirmations.peek(token, admin_id)` instead of encoding it in the callback
  data.** §S1-5.1 puts *all* confirmations through one handler, but
  `Confirmations.consume(token, admin_id, action)` verifies the action, and the
  callback data (``cf:<token>``) deliberately never carries it — that is what
  lets the copy say «Старая ссылка перестанет работать» while the token stays a
  bare secret. Three options were on the table: put the action in the payload
  (duplicates state the store already holds, eats the 64-byte budget the module
  docstring warns about, and lets a crafted payload *choose* an action), change
  `consume` to not take an action (drops the "this token is for that action"
  binding and rewrites M0-07's tests), or read the action first. `peek` is
  non-destructive and owner-checked, so the pair `peek` → `consume` (no ``await``
  between them, hence atomic in the single-threaded loop) keeps every existing
  guarantee and adds one method.
- **«wrong user → fresh card» is implemented as "the stranger burns nothing".**
  `peek` returns ``None`` for a token that belongs to somebody else, so the
  intruder gets the «подтверждение устарело» toast and the **owner's** token stays
  live; asking 🔄 again mints a *fresh* card (a new token). A literal reading —
  render a new confirmation card *for the intruder's own* action — is impossible
  to do generically (the dispatcher does not know which screen minted the token),
  and forcing it would either re-mint arbitrary actions for anyone who presses a
  forwarded button or require per-action cancel/re-render hooks. The test asserts
  both halves: the intruder is refused and the owner's token still consumes.
- **«❌ Отмена» is answered generically: the dispatcher drops the token and edits
  the card to `texts.CONFIRM_CANCELLED` (no keyboard).** A cancel button cannot
  know which screen to restore either, and the alternative — leaving the card on
  screen with two now-dead buttons — is worse. Making the cancelled card generic
  (plus a «Отменено» toast) keeps the one-handler rule true: a future action
  registers one callable and gets confirm *and* cancel for free.
- **`Container.init_confirmations()` is a separate init method, not folded into
  `init_rbac()`.** Every other service has its own `init_*` (`init_audit`,
  `init_panel`, …) called from `run()`/`conftest`; the confirmation store is not
  RBAC (it is used by user-facing screens), so bundling it into `init_rbac` would
  have made the name lie. It needs no sessionmaker — the store is purely
  in-memory — which is exactly why it is not a field the DB layer owns.

- **The 10-minute cooldown lives in `profile.py` as a module-level
  `_last_regen: dict[int, float]`, keyed by ``tg_id`` and fed a `time.monotonic()`
  stamp.** §S1-5.4 prescribes the dict, and monotonic time is the right clock for
  a rate limit (a wall-clock jump must not unlock or lock the button). It is
  checked in **both** entry points — `prf:newlink` (before minting a card, so a
  user cannot queue two regenerations) and the `newlink` action (the card can be
  pressed minutes later) — and stamped **only** after `regenerate_sub_id`
  returned, so a panel failure never starts the clock. Tests clear it with an
  `autouse` fixture because module state would otherwise leak between cases.
- **A failed regeneration does *not* re-render the dashboard — it shows
  `texts.NEWLINK_FAILED`.** On `PanelError` the old ``sub_id`` is untouched, so
  «Старая ссылка продолжает работать» is factually true; re-running
  `_resolve_target` would issue a *second* panel read that can fail on its own
  (turning a clear "link not changed" into an outage card) and would hide the
  reason. The success path *does* re-render (`_show_profile`), which reads the
  panel once more — the cache was invalidated by the write, so the card shows the
  fresh link and the QR button, and that screen answers the callback itself (no
  double `answer_callback_query`).
- **`regenerate_sub_id` got a post-write identity check *in addition to* the
  existing `mutate` verify.** `mutate` already re-reads bypassing the cache and
  raises ``PanelError`` when the value did not stick, so the extra
  `fresh.sub_id == previous` guard is defence in depth; it is what §S1-5.0 asks
  for ("raise if the new id is empty/equal") and it is unit-tested against a
  panel that silently drops the update. `scripts/smoke_panel.py` mirrors the same
  invariant on the live panel (`regenerate.changed` + `traffic_matches` →
  `regen_ok`), so the operator run proves the old link really died.

- **`PAYMENT_USER_APPROVED` now takes `{expiry}` instead of `{days}`, and a
  separate `PAYMENT_USER_APPROVED_UNLIMITED` carries the perpetual case.** §S1-5.6
  asks for «Подписка до …», and a message cannot `format` a date it did not get:
  `PaymentService._user_approval_text` selects on the *falsy* `expiry_after_ms`
  (``None`` **or** ``0`` → unlimited, everything else → `_expiry_label`), which is
  the "not `or 0`" rule from §S1-5.7 — ``or 0`` would have formatted the epoch.
  The one existing test that pinned the old two-argument string now derives the
  expected expiry from the persisted row, so the assertion checks the *content*
  (the granted date) rather than a copy-pasted literal.
- **`_notify_user` gained a keyword-only `reply_markup`; `Notifier` needed no
  change.** `safe_send` already forwards ``**kwargs`` to `send_message`, so the
  post-payment buttons cost one parameter. `BUTTON_GO_PROFILE` /
  `BUTTON_GO_SUPPORT` are **aliases** (`is`) of the menu labels, reusing the S1-4
  argument that two literals for one destination eventually drift; the buttons are
  built by a small `_go_markup(section, label)` helper with the same lazy
  `quick_markup`/`ProfileNav` import style `retry_markup` already used, so the
  service keeps no telebot import at module scope.
- **Tests went where the code lives.** The panel hardening case joined
  `tests/test_panel_gateway.py` (next to the existing `regenerate` test), the six
  handler cases joined `tests/test_handlers_start_profile.py` (the file of the
  S1-1–S1-4 screens, as PROGRESS prescribes), the copy/alias assertions joined
  `tests/test_text.py`, and the payments assertions stayed in
  `tests/test_payments.py`. No new test module: each S1-5 change touches an
  existing surface.

## S2-2 — Users list, filters and search

- **The list is DB users joined with *one* cached panel read.** `load_rows` calls
  `panel.list_clients()` once and indexes it by ``email`` (the panel stores the
  Telegram id there), then pairs each ``users`` row with its client. A page render
  therefore costs a single panel call regardless of page size, and both failure
  modes degrade instead of blanking the screen: a panel outage maps to an empty
  map (every row becomes clientless → 🔴) and a DB error to an empty list.
- **`UserRow.expiry_ms`/`enable` are ``None`` for a clientless user**, so "no
  panel client" and "panel unavailable" are deliberately indistinguishable on
  this screen — both render 🔴. That is the safe direction: a staff member never
  sees a stale 🟢 for an account whose client they cannot confirm.
- **The filter key is ``blocked`` but it selects the 🔴 icon, not the ⛔ bans.**
  §S2-2's filter row is `[Все] [🟢] [🔴] [🟡 скоро]` while PROGRESS names the keys
  `all|active|blocked|soon`, so ``blocked`` is the red group (expired/**disabled**
  — i.e. frozen or never-activated clients). Banned (⛔) and pending (⏳) rows have
  their own icons and appear only under «Все»; S2-2 has no dedicated filter for
  them. A future ``banned`` filter can be added without renaming this one.
- **`status_icon` order of checks fixes the edge cases:** blocked ⛔ → pending ⏳ →
  any other non-approved status 🔴 → an approved row needs *both* a client and
  ``enable`` to leave 🔴 → an enabled ``expiry == 0`` is unlimited 🟢 → the 3-day
  window is a **strict** ``left > 3 d`` for 🟢, so exactly three days is already
  🟡 (the AC's boundary), and ``left <= 0`` is 🔴. ``new``/``rejected`` fall
  through to 🔴 because they are simply not active.
- **Search is exact on ``tg_id`` for digits and case-insensitive on ``username``
  otherwise**, with a leading ``@`` stripped first and a blank query returning
  ``[]`` — matching §S2-2.1's "exact id / case-insensitive name" split. It is one
  repository function so the SQL stays out of the handler.
- **`list_screen` *is* the registered `adm:users` screen and it parses its own
  payload.** The nav dispatcher calls every screen as
  ``screen(call, bot, container, payload)``, so `list_screen` takes the payload as
  its 4th argument and keeps PROGRESS's keyword-only ``page``/``filter_key`` as
  fallbacks (used by tests). `_route` reads ``adm:users:p:<n>`` / 
  ``adm:users:f:<key>``; the 2-segment ``adm:users`` clears the FSM state, which
  makes the plain list button double as the search prompt's «✖️ Отмена»
  (§S2-2.8's "cancel returns to the list and clears the state").
- **A search hit renders a one-row list, not the user card.** The card is S2-3,
  and its ``adm:users:card:<id>`` action would route back through *this* screen —
  opening it now would either dead-end or require a forward reference to unbuilt
  code. Rendering the filtered list puts the card button on screen and makes the
  AC ("id + username reach the card") true as a button payload, with the card
  itself arriving unchanged in S2-3.
- **The keyboard is built with ``telebot.types`` directly, not ``quick_markup``.**
  The page mixes row widths — one full-width button per user, then a 4-button
  filter row, a search row and the prev/next row — and ``quick_markup`` applies a
  single ``row_width``. Button captions are plain text (Telegram does not parse
  them), so only the header line is HTML and carries no user-supplied strings.
- **Registration is import-driven.** ``@register_screen("users")`` runs when the
  package imports the module, so `app/handlers/admin/__init__.py` imports it and
  the dashboard's "is this screen live?" check sees ``users`` immediately;
  ``register_users_handler`` adds exactly the ``UserStates.admin_search`` message
  handler and is called from ``register_admin_handler`` (one message + one
  callback handler still, per §S2-1.2).

## S2-3 — User card and one-tap actions

- **One callback namespace, one handler.** The card and all fourteen actions ride
  the existing ``adm:`` handler (§S2-1.2): ``list_screen`` calls
  ``user_card.route(call, bot, container, payload)`` *first* and returns when the
  payload is one of :data:`CARD_OPS`, so ``adm:users:card:<tg_id>`` and every
  action stay inside the single registered callback — no new telebot handler that
  first-match ordering could shadow (the same reason ``cf:`` exists).
- **The action name carries its parameter.** ``AdminNav`` is
  ``adm:<section>[:<action>[:<arg>]]`` — one optional arg slot, and the *target*
  id has to live there (``callbacks.py``: never encode the clicker, target ids are
  fine). §S2-3's shorthand ``gr:7``/``lim:50`` therefore cannot be encoded
  literally: 5 segments are unparseable. Actions are
  ``adm:users:<op>:<tg_id>`` with the parameter folded into ``<op>``
  (``gr7``/``gr30``/``grc``, ``lim10``/``lim50``/``lim100``/``liminf``, ``fz``,
  ``uf``, ``rt``, ``nl``, ``wr``, ``ban``, ``unban``, ``del``), which is also why
  :data:`OP_PERMISSIONS` is a flat map rather than nested.
- **Permissions are enforced per op, in the mutation handler.**
  ``_run_action`` maps each op to ``USERS_EDIT``/``USERS_BAN``/``USERS_DELETE`` and
  calls ``check_callback`` *before* dispatching, and both ``cf:`` actions check
  again (a role can be revoked between the question and the answer). The
  ``adm:users`` gate is only ``USERS_VIEW``, so a ``support`` user sees a
  view-only card and a *forged* button still gets the denial alert. The keyboard
  uses the same ``role_has`` checks, which makes hiding a button cosmetic by
  construction.
- **``card_keyboard`` labels the ban button from ``enable``, not from the DB
  status.** §S2-3.3 fixes the signature at
  ``card_keyboard(role, tg_id, *, enable, unlimited)``, so a disabled client shows
  ✅ Разбан (a banned client is disabled by construction). The label is only
  affordance: pressing ✅ on a merely frozen user runs ``UserService.unban``, which
  flips the status to ``approved`` and re-enables the client only when the
  subscription is still live — no state corruption, just a redundant write. A
  future segment can pass the DB status if the nuance ever matters.
- **``unlimited=True`` only changes the custom-grant label.**
  ``SubscriptionService.grant_days`` returns ``changed=False`` with
  :data:`UNLIMITED_REASON` for a truly perpetual client (``expiry == 0`` **and**
  enabled); the card re-renders and shows that reason as an alert instead of
  inventing an expiry, and the ``✏️ N дней (∞)`` caption warns before the press.
- **The card's traffic and limit values are bytes at the boundary.**
  ``set_limits`` is called with ``gb_to_bytes(gb)`` (``∞`` → ``0`` = no quota)
  exactly like §S2-3.8 says, and ``render_card`` formats ``ClientTraffic.total``/
  ``used`` with ``fmt_bytes``. The gateway writes ``total_gb`` but reads
  ``Client.total`` back (S0-2.4's open unit question), so ``FakePanel.set_limits``
  now mirrors the value into **both** fields — otherwise a limit set through the
  card would read back as «∞» in the double.
- **Three independent reads, none of which can fail the render.** ``load_card``
  reads the ``users`` row, the panel snapshot and ``payments_repo.user_totals``
  separately: a missing row → ``None`` (→ «Пользователь не найден»), a panel outage
  → :data:`PANEL_WARNING` + «Нет клиента на панели», a failing payments query →
  ``0``. The card is the one screen an admin needs *during* an outage, so it
  degrades instead of erroring.
- **The payments line is gated at render time, not at read time.**
  ``render_card(..., can_view_payments=role_has(role, PAYMENTS_VIEW))`` — the
  figures are read for every viewer (one cheap query) but only a role with
  ``payments.view`` sees them, so a ``support`` card can never leak revenue.
  ``user_totals`` counts ``approved`` rows only, keeping declined/revoked attempts
  out of the figure.
- **Delete keeps the history: panel first, row second.** The ``cf:`` action removes
  the panel client (``ClientNotFound`` = already gone, not an error) and only then
  flips the row to ``rejected`` with ``note="deleted by admin"`` — the payments
  rows are untouched, and a panel failure aborts before the status changes, so
  there is never a live client with no row. The user is gone, so the card's
  message re-renders the *list* it was opened from.
- **``wr`` reuses the support relay instead of growing a second one.**
  ``support.enter_writing_to_user`` is the single entry point behind both
  ``/support_user <tg_id>`` and the card's «✉️ Написать»: same
  ``UserStates.writing_to_user``, same ``target_user_id`` FSM key, so
  ``support_relay`` delivers through ``Notifier.safe_send`` either way. The card
  variant is a mutation, so it is additionally gated by ``USERS_EDIT`` (the
  command keeps its ``SUPPORT_REPLY`` requirement).
- **The day-count prompt drops its state on every exit.** ``grc`` sets
  ``UserStates.admin_grant`` and stores the target in the FSM data (never in the
  message text — a stray number must not pick a victim). The prompt's «✖️ Отмена»
  is the card's own payload, so ``card_callback`` clears the state and re-opens the
  card; a reply that is not a number is answered and the state cleared too, so a
  typo cannot swallow the admin's next message. The prompt message is edited into
  the refreshed card afterwards.
- **Ban/unban write their own audit row via the service.** ``UserService.ban``/
  ``unban`` already log ``user.ban``/``user.unban``; the card only adds the user
  notice (``BAN_USER_NOTICE``/``UNBAN_USER_NOTICE``) and the toast, and keeps the
  ``/ban`` rule that staff are never bannable. Every other action audits through
  ``_audit`` (``user.grant_days``, ``user.freeze``, ``user.unfreeze``,
  ``user.limits``, ``user.reset_traffic``, ``user.sub_regenerate``, ``user.write``,
  ``user.delete``).

## S2-4 — Payments section (queue, history, stats)

- **One screen, four payloads — no second callback namespace.** ``adm:payments``
  is registered once (§S2-4.2) and routes itself: ``adm:payments`` renders the
  home, ``:p:<page>`` the pending queue, ``:h:<page>`` the history, ``:st`` the
  stats card and ``:c:<id>`` sends a review card. The dispatcher hands the screen
  the already-unpacked ``AdminNav``, so the section needs *no* new button handler
  and every payload stays a plain ``AdminNav.pack()`` — the same shape as the
  users list (§S2-2). A garbage page arg degrades to page ``0``
  (``_page_arg``), and an unparseable id answers «Кнопка устарела» rather than
  raising (§B5).
- **`payments_repo.stats` is a rename of `revenue_since`, not a second query.**
  §S2-4.1 asks for ``stats(session, *, since) -> tuple[int, int]`` while the S2-1
  dashboard already reads ``revenue_since``. Two implementations of “approved
  **and applied** since X” would be two chances to drift — and one of them would
  eventually forget to exclude declined/revoked — so ``stats`` *is*
  ``revenue_since``. There is exactly one place that decides what money counts,
  and the dashboard's 30-day counter and this card can never disagree.
- **A queue row opens the real card, delivered rather than re-rendered.**
  ``render_review_card``/``review_markup`` are the public halves of what the
  submit path already built inline, so the queue reuses the *standard* card
  instead of a copy of it (§S2-4.3). The card is sent through
  ``Notifier.send_card``, which registers it as a card copy — deliberately not an
  in-place edit of the list message: ``admin_cards`` lets the existing
  ``pay:ok``/``pay:no`` handlers keep this copy (and every other staff copy) in
  sync once the decision lands, whereas an edit would leave a live approve button
  on a decided payment. The list stays where it was; «⬅️ Назад» returns to it.
  A payment deleted in the meantime answers ``PAYMENT_NOT_FOUND`` instead of
  crashing.
- **Windows are calendar days in the configured timezone, and the chart *is* the
  «7 дней» window.** All boundaries are local midnights converted to naive UTC
  (the app stores naive UTC): «Сегодня» = today's midnight, «7 дней»/«30 дней» =
  6/29 days back, «Всего» = ``EPOCH``. Calendar windows (not rolling ``now - 7 d``)
  because that is what an admin reads as “today/this week”, and it makes the
  seven bars sum *exactly* to the «7 дней» figure. Each bar is
  ``rev(day) - rev(day - 1)`` from a **cumulative** series — one ``stats`` read per
  boundary instead of one per day-with-its-own-query — and ``max(0, …)`` floors a
  clock skew/boundary artefact into an empty bar rather than a negative one.
  ``peak`` scales the bars, so the busiest day fills ``bar()`` and a quiet day is
  empty.
- **The bars are the section's only copy of a number.** Labels are inline
  (``TASK_PLAN.md`` rule 9: a screen is layout, not copy), and ``render_stats``
  takes a frozen ``Stats``/``WindowStats`` rather than reading the DB, which is
  what makes the fixture test possible (§S2-4.5 AC) without a live session.
- **History rows are informational and point back at their own page.** A decided
  payment has nothing to approve and we have no read-only card, so a row carries
  ``adm:payments:h:<page>``: clicking simply re-renders the page it is on
  (``edit_or_send`` treats “message is not modified” as success). An inert
  ``noop`` ``callback_data`` was avoided on purpose — no registered handler owns
  that namespace, so the click would hang the client spinner and log an
  unhandled callback, exactly the B5 class of wart.
- **One users read for the whole page, and every read degrades.** Rows only carry
  ``user_tg_id``, so the page joins a single ``users_repo.list_all`` map (§S2-4.3)
  instead of a query per row; a missing username shows
  ``PAYMENT_NO_USERNAME``. The list/count/stats/users reads are each wrapped in
  try/except and degrade to ``[]`` / ``0`` / a zeroed ``Stats`` — the payments
  screen is what an admin opens *because* something looks wrong, so it must render
  even when a query fails.
- **The screen re-checks `PAYMENTS_VIEW`.** The ``adm:`` dispatcher already gates
  the section, but a forged payload must also be refused by the screen itself
  (defence in depth, as in every other §S2 screen); ``support`` — which holds
  ``users.view`` but not ``payments.view`` — sees neither the dashboard button nor
  the section.


## S2-5 — Server screen and Xray restart

- **`restart_xray()` replaces the old `NotSupportedError` with a raw POST.** The
  route is the one confirmed from the 3x-ui source in M0-03
  (`POST {domain}/panel/api/server/restartXrayService`, `Authorization: Bearer
  <VPN_TOKEN>`) and is called exactly like the existing raw
  `resetClientTraffic` fallback: `self._call(lambda: self._restart_xray_raw())`,
  so a transport error maps to `PanelUnavailable` and `raise_for_status()` keeps
  a non-2xx response from passing as success. `py3xui` 0.7.0 still has no
  wrapper, so there is nothing to prefer over the raw call. It is **never**
  invoked by bot logic on its own — only the owner's confirm-gated button.
- **The panel's `/server/status` field names are still `unverified`.** No live
  probe was made (the smoke script is operator-gated), so `render_server` accepts
  the shapes `TASK_PLAN.md` §S2-5 lists and nothing else: `cpu` as a percentage,
  `mem`/`disk` as either a percentage or a `{current, total}` byte pair, `uptime`
  in seconds, `xray` as a state string or `{state, version}`, and `online` as an
  int. Whatever the real payload does not return simply drops its line (a missing
  field never becomes a fabricated `0%`). **Whoever runs the S0-2 smoke script
  should paste the real `/server/status` key names here** and the mapper can be
  tightened to them.
- **The screen is layout, not copy (rule 9).** Labels, the `CPU`/`RAM`/`Диск`
  bar lines and the `⏱ Аптайм · Xray · онлайн` summary live inline in
  `app/handlers/admin/server.py`; `bar()` from `app.ui` draws the bars so the
  look matches the profile/limits bars elsewhere.
- **Two permissions, checked in two places.** `adm:server` is gated by
  `SERVER_VIEW` (the nav dispatcher *and* the screen re-check it), but the
  restart is owner-only `SERVER_RESTART`: the button is only offered when
  `role_has(role, SERVER_RESTART)`, the `rs` action re-checks it before minting a
  token, and the registered `cf:` action checks it a third time — a role revoked
  between the question and the answer still cannot restart. Hiding the button is
  cosmetic; the three checks are what enforce it.
- **The restart is confirm-gated through the shared `cf:` store.** `adm:server:rs`
  mints a `server_restart` token (`container.confirmations`) and shows the
  standard `[✅ Подтвердить][❌ Отмена]` card — no write happens until the token
  is consumed by the central `cf:` dispatcher (§S1-5.1), which is why no new
  telebot callback handler is needed. The registered action restarts, sleeps
  `RESTART_SETTLE_S` (3 s, a module constant so tests set it to 0 before the
  status re-read), reports `✅ Xray перезапущен` + the fresh card, or
  `ERROR_PANEL` on failure, and always records a `server.restart` audit row.
- **`FakePanel` toggles `xray_running` instead of raising.** Its `restart_xray`
  now records the call for `panel.calls` and flips a boolean that
  `server_status()` reflects in the `xray` state — enough for the handler test to
  assert that a restart really happened (and that the confirmed action, not the
  button, performed it). `FakePanel.server_status` grew a fuller payload so the
  screen test exercises every line.
- **One S2-1 test moved with the new screen.** Registering `adm:server` (it is
  imported by `app/handlers/admin/__init__.py`, so `@register_screen("server")`
  runs at import) makes the dashboard's `🖥 Сервер` button live, so
  `test_dashboard_keyboard_filters_by_role_and_registry` expects it; with S2-6 the
  same test now also expects `📢 Рассылка` and uses the still-unregistered
  `audit` section as its "no dead button" example.


## S2-6 — Broadcast with preview and progress

- **`active` and `soon` are panel-refined, not two copies of the approved set.**
  `TASK_PLAN.md` §S2-6.2 words `active` as "the approved set", but the approved
  set is exactly the ``all`` audience minus nothing — two buttons with identical
  recipients. The 🟢 icon means "enabled, not expired" everywhere else in the
  admin UI, so `active` = reachable users whose panel client is enabled and whose
  `expiry_time` is 0 (unlimited) or in the future, and `soon` = reachable users
  expiring within `SOON_WINDOW_MS` (7 days). `all` stays the reachable approved
  set (`users_repo.list_broadcast_ids`), so ``bot_blocked`` can never be targeted
  (§S2-6.5's "blocked skipped" is enforced at resolution *and* again by
  `safe_send` marking `bot_blocked` on a 403).
- **A panel outage degrades the audience, it never fails the flow.**
  `_client_state()` returns `{}` when `panel.list_clients()` raises, so
  `active`/`soon` collapse to "nobody" rather than aborting a broadcast an admin
  already previewed. `_reachable_ids()` likewise returns `[]` on a DB error. Both
  are read once, in one short session that closes *before* the send loop — the
  legacy §M0-09.4 guarantee (no DB connection held across the pacing sleeps) is
  asserted by a session-counting proxy in the tests.
- **The progress card and the summary are `edit_or_send` on one message.**
  §S2-6.5 asks for "a live progress message … then one final summary", so the same
  message is edited every `PROGRESS_EVERY` (20) sends and finally replaced by the
  summary — a broadcast of 10 000 users adds **no** messages to the chat beyond
  the recipients' copies. `edit_or_send` swallows Telegram's "message is not
  modified" error, so an admin flicking between two screens cannot break it.
- **`/broadcast <text>` opens the audience step, it no longer sends.** The legacy
  handler fanned out immediately; that made a typo unrecoverable and left no room
  for an audience choice. It now sets the `admin_broadcast` state and stores the
  text, exactly like the prompt path, and the admin still passes through
  audience → preview → `[✅ Отправить]`. This is a deliberate behaviour change
  (the §S2-6.6 AC is "reaches the preview with the given text").
- **The pending text/audience live in the telebot FSM data, and the state is kept
  alive until the end.** `StateMemoryStorage.delete_state()` deletes the state
  *and* the data together, so the flow only clears the state when it is finished
  (after send, or via «✖ Отмена»); clearing it earlier would silently lose the
  text on the next callback. `bot_blocked`-users are dropped before the preview,
  so the count the admin confirms is the count that gets sent.
- **`patient=True` is opt-in and only the broadcast uses it.** `safe_send`'s new
  keyword threads through `_deliver`/`_handle_api_error`: in patient mode a 429
  sleeps the **full** `retry_after` (ignoring `MAX_RETRY_AFTER`) and retries once;
  every other caller keeps the capped behaviour (§2.9), so a stray 429 on a
  routine notification cannot park a handler for a minute.
- **One new test module, three rewritten/added assertions elsewhere.** The full
  flow lives in `tests/test_handlers_admin_broadcast.py` (§S2-6.7); the two
  non-flow cases (usage hint, `broadcast.send` refusal) stay in
  `test_handlers_support_broadcast_ban.py`, whose §M0-09.4 session test now drives
  the real command → audience → send path; `test_notifier.py` gains the patient
  429 case and `test_handlers_admin_home.py` the new dashboard button.


## S2-7 — Settings screen

- **Both writes go through the existing `setting.set` audit action.** `/maintenance`
  already records `setting.set` with `target_type="setting"`,
  `target_id="maintenance_mode"`; the screen records the same action/target and
  adds **`old`/`new`** to `details` (the §S2-7 AC asks for old → new). Keeping one
  action string means a single audit query sees every settings change no matter
  which entry point made it — a new action name (`settings.toggle`) would have
  silently split the trail in two.
- **The maintenance toggle re-checks `maintenance.toggle`, the screen checks
  `settings.edit`.** The `adm:` dispatcher and the screen both gate the section on
  `SETTINGS_EDIT` (owner-only), and the toggle re-checks the narrower
  `MAINTENANCE_TOGGLE` right before the write — the same defence-in-depth rule the
  user card (§S2-3) and the server restart (§S2-5) follow: hiding a button is
  cosmetic, the write is what must be refused. A forged `adm:settings:mt` from an
  `admin` is covered by a test that calls the screen directly (bypassing the
  dispatcher's own refusal).
- **The bank details are confirmed through the central `cf:` store, not an
  `adm:` op.** A bank value is multi-line and arbitrarily long, so it cannot be
  encoded in (64-byte) callback data the way the other screen actions are. The
  prompt stores it server-side in a `Confirmations` token and the preview card
  carries the standard `[✅ Подтвердить][❌ Отмена]` pair — the same indirection
  §S1-5.1/S2-5 use, which also inherits the token's admin binding and TTL for free.
- **«✖️ Отмена» is the settings home itself.** The prompt's cancel button is
  `adm:settings`, and the home branch clears the `admin_bank` FSM state before
  rendering, so cancelling both drops the state and re-opens the card — the same
  trick `adm:users:card:<id>` uses for the custom-grant prompt (§S2-3.6). Nothing
  is written until the confirm, so «cancel keeps old» holds by construction.
- **No explicit `SettingsService.invalidate` call is needed.** `set()` refreshes
  its own cache entry with the new value, so the very next `/pay` read (same
  process) is already fresh; the AC's "cache invalidated" is covered by the write
  path itself, and the test drives the real `pay:sel` handler instead of poking the
  cache to prove it.
- **The screen only reads what it needs, and degrades.** `_read()` returns
  `(False, None)` when `SettingsService` is missing or a read raises, so the card
  renders the defaults rather than blanking out — the settings screen is on the
  Checkpoint-B path and must never be the screen that fails to open.


## S4-1 — Per-role command menus

- **The menu lists only commands that exist.** Default scope `/start /profile
  /pay /support /help`; staff `+ /admin /support_user`; `admin`/`owner`
  `+ /broadcast /ban /unban /banned_list /maintenance`. §S4-1's example also
  names `/invite`, but §S3-3 has not registered that handler yet — a menu entry
  that opens nothing is the command-line twin of a dead button (§S2-1), so it
  joins the table in S3-3 instead.
- **`support` gets `/admin` too.** The plan's literal list gives support only
  `/support_user`, but support holds `users.view`, so `adm:menu` already works
  for them and `/start` already shows them «🛠 Админ-панель». Advertising it in
  the menu keeps the two surfaces honest; the dashboard still filters its
  sections by permission, so support sees no more than before.
- **Staff are enumerated through `users.view`, not a new service query.** Every
  role of §2.5 holds `users.view`, and owners come from `OWNER_IDS` inside
  `AdminService`, so `staff_with_all(Permission.USERS_VIEW)` is exactly the set
  of chats that needs its own scope — one source of truth for the permission
  matrix, no new repository method (`_all_admins` stays private).
- **A rejected per-chat publish is logged, not fatal.** `setMyCommands` with a
  `BotCommandScopeChat` answers `400 chat not found` until that staff member has
  written to the bot, so `_publish_chat` swallows the error per chat: one quiet
  owner cannot cost everybody else their menu, let alone abort startup.
- **The legacy `delete_my_commands()` round trip is gone.** `setMyCommands`
  replaces the list of the scope it is given, so the old "start clean" delete
  bought nothing. Consequence: a **revoked** admin keeps their per-chat menu
  until it is re-published or cleared — that belongs to D-4, which is where
  `admins` rows are written, and `setup_bot_commands` is the function it calls.
- **The tables live in `app/commands.py`; `setup_bot_commands(bot, container)`
  is the only entry point.** `app.run` calls it once at startup in place of the
  old owner-only `_publish_command_menus`, and the descriptions mirror
  `texts.HELP_TEXT` so the "/" menu and `/help` cannot describe the same command
  in two different ways.
